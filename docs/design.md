# 本地语音识别设计

## 浏览器与后端

FastAPI 同时提供静态前端和识别接口。原生 JavaScript 用 MediaRecorder 录制 Chrome 或 Edge 生成的 WebM 音频；录音结束时汇总数据，用与文件上传相同的 multipart 请求提交。等待麦克风授权、录音及识别期间，页面锁定可能冲突的输入操作。录音停止或失败后，统一清理麦克风轨道、计时器、录音事件监听和音量监测。

后端限制请求体及文件大小，并校验语言和扩展名。解码器直接读取 multipart 上传流，普通上传时长不限。对于网页录音，标准 PCM WAV 由 Python `wave` 按帧数检查时长，WebM 等格式由 PyAV 在重采样过程中按采样数检查时长。两条路径均交付 16 kHz 单声道 float32 波形。解码和推理串行执行，避免并发请求同时持有多份解码波形。

## 模型与错误处理

自动模式先在 CPU 启动。中文优先使用 FunASR Paraformer INT8，英文和 FunASR 无法使用时由 Whisper `base` INT8 转写。后台完成 CUDA 实际推理验证后，后续请求使用 Whisper `large-v3-turbo`。CUDA 推理失败时按语种回退 CPU 并重试该请求。模型优先取自根目录的 `models/`。

默认启动时加载一次模型。可选择在首个有效识别请求时加载，重复加载由锁保护。懒加载耗时从响应的处理耗时扣除。解码与推理运行在线程池，单进程的 CPU 模型将推理串行化，单次推理失败时重试一次。客户端收到的错误包含可执行的提示，服务日志记录定位所需的异常和请求编号。

静态资源由本机服务提供，权重准备后可使用 `HF_HUB_OFFLINE=1` 启动。用户音频只发往这个 FastAPI 服务，项目没有识别历史存储。

## 录音期间转写

浏览器在同一个麦克风流上运行 AudioWorklet，每累计约 4 秒便生成一份独立的单声道 PCM WAV。前端逐段调用现有识别接口，每次只有一个实时片段请求在途，返回的非空文本按录音顺序追加。短句跨片段时，阶段文本可能有断句或漏词，预计显示延迟为一个片段的采集时间加上本地处理和排队时间。

手动停止或达到 60 秒时，前端丢弃排队片段并取消等待在途预览响应。已开始的服务器推理可以完成。MediaRecorder 的完整 WebM 仍交给现有接口，最终结果替换阶段文本。片段识别失败会提示用户，录音和最终识别仍可继续。整个录音流程使用同一语言设置，模型取决于提交时的设备状态。
